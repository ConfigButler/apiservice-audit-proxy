1. Create or provide the webhook kubeconfig Secret referenced by `audit.webhook.kubeconfigSecretName`.
2. Set `backend.url` to the real aggregated backend this proxy should forward to.
3. Choose one serving certificate path with `server.tls.mode`:
   - `existing-secret`: mount an existing TLS Secret with `tls.crt` and `tls.key`
   - `self-signed`: chart generates a self-signed CA + cert, embeds the CA into the `APIService.spec.caBundle`, and preserves the Secret across upgrades via lookup
   - `cert-manager`: let cert-manager issue the serving cert and inject the CA into the `APIService`
4. If the backend requires custom trust or mTLS, set `backend.tls.caSecretName` and/or, in requestheader mode, `backend.identity.requestheader.clientCert.secretName`.
5. If you enable `server.apiService.enabled` with `server.tls.mode=existing-secret`, set either `server.apiService.caBundle` or `server.apiService.insecureSkipTLSVerify=true`.
6. Metrics are served on the `metrics` Service port when
   `metrics.listenAddress` is not `0`. Plain HTTP by default; set
   `metrics.tls.enabled=true` with `metrics.tls.secretName` to serve over
   HTTPS. Enable either `metrics.serviceMonitor.enabled` or
   `metrics.vmServiceScrape.enabled` to render scraper resources.

Example:

  helm upgrade --install {{ .Release.Name }} {{ .Chart.Name }} \
    --namespace {{ .Release.Namespace }} \
    --create-namespace \
    --set backend.url=https://sample-apiserver.wardle.svc:443 \
    --set audit.webhook.kubeconfigSecretName=audit-pass-through-webhook-kubeconfig \
    --set server.tls.mode=self-signed
